React Native Docs — Phase 2 Fixes for Review

5 fixes applied (1 in SDK source, 4 in docs), each cross-referenced against the RN SDK on the release/2.8.0 branch and against the iOS/Android SDK source on master.

This is the first review pass for the React Native docs (which were not part of an SDK README port like iOS and Android). The docs were audited against the live TypeScript types and the Expo sample app, and the TS types themselves were cross-checked against the iOS and Android SDK source. The defects below were found and fixed; outside-scope items follow at the bottom. Build verified clean (pnpm build, zero broken-link warnings).

Group 1 — SDK type misalignment with iOS/Android

1OmetriaBasket.link was wrongly required in TypeScript

Files: src/types.ts, src/NativeOmetriaReactNativeSdk.ts
-export type OmetriaBasket = { id?: string; currency: string; totalPrice: number; items: OmetriaBasketItem[]; link: string; };
+export type OmetriaBasket = { id?: string; currency: string; totalPrice: number; items: OmetriaBasketItem[]; link?: string; };

Why: The RN TypeScript type declared link as required, but iOS and Android both declare it optional. A developer calling trackBasketUpdatedEvent({...}) without link would get a spurious TS compile error even though the underlying native SDK accepts it fine. The fix makes RN consistent with iOS/Android and removes the need to populate a placeholder URL on every basket call. Same change applied to both src/types.ts and the TurboModule spec src/NativeOmetriaReactNativeSdk.ts (codegen requires the inline type).

SDK source (other platforms):

  • iOS/Sources/Ometria/OmetriaBasket.swift: var link: String?
  • Android/.../core/event/OmetriaBasket.kt: val link: String? = null
Both use an optional/nullable link. RN was the outlier.

Group 2 — Bug in the Quick Start example

2Quick Start fired trackProfileIdentifiedByEmailEvent before initialization resolved

File: docs-react-native/intro.md § "Quick Start" → step 3
-Ometria.initializeWithApiToken('YOUR_API_KEY'); // Track user identity Ometria.trackProfileIdentifiedByEmailEvent('user@example.com');
+Ometria.initializeWithApiToken('YOUR_API_KEY').then(() => { // Track user identity Ometria.trackProfileIdentifiedByEmailEvent('user@example.com'); });

Why: initializeWithApiToken returns a Promise<void>. The original Quick Start fired the next call synchronously, before the promise resolved — which contradicts installation.md's own warning ("Any other Ometria methods must be called after initialization"). Switched to .then(...) to match the pattern used in the Expo sample app (example-expo/src/App.tsx).

SDK source: src/types.ts declares initializeWithApiToken: (token: string, options?: OmetriaOptions) => Promise<void>. The sample app uses Ometria.initializeWithApiToken(token, customOmetriaOptions).then(async () => { … }).

Group 3 — Documentation/data inconsistencies

3Removed their_id jargon from customer-facing docs

File: docs-react-native/events/product-events.md § "Listing Attributes"
-| `id` | `string` | The attribute `their_id` that exists in the Ometria database (e.g., "red") |
+| `id` | `string` | The attribute identifier as it exists in the Ometria database (e.g., "red") |

Why: their_id reads like an internal database column name. Same wording was already corrected in the iOS and Android docs; React Native is now consistent with both.

4Sample-app GitHub URL: wrong repo slug and wrong branch (3 occurrences)

Files: docs-react-native/intro.md (×2), docs-react-native/troubleshooting.md, docs-react-native/push-notifications/notification-service-extension.md
-https://github.com/Ometria/ometria.react-native-sdk/tree/main/example-expo
+https://github.com/Ometria/ometria.react_native_sdk/tree/master/example-expo

Why: The published repo is ometria.react_native_sdk (underscores) on master; the docs linked to ometria.react-native-sdk on main, both 404 today. The example-expo/ directory exists locally on the release/2.8.0 branch and will land on master when 2.8.0 ships — at which point these URLs will resolve.

SDK source: git remote -v on the local working tree shows github.com:Ometria/ometria.react_native_sdk.git; gh api repos/Ometria/ometria.react_native_sdk confirms "default_branch": "master".

5RN events sidebar collision (basket-events and screen-events both at position 4)

Files: docs-react-native/events/screen-events.md, docs-react-native/events/custom-events.md
-screen-events.md sidebar_position: 4 custom-events.md sidebar_position: 6
+screen-events.md sidebar_position: 6 custom-events.md sidebar_position: 7

Why: basket-events.md (4) and screen-events.md (4) shared a position — Docusaurus picked an alphabetical fallback so the sidebar still rendered, but the order didn't match either file's frontmatter intent. Renumbered to mirror the iOS/Android event-page ordering: overview 1, profile 2, product 3, basket 4, order 5, screen 6, custom 7.

Outside scope (not fixed in this pass)

  • SDK typo: OmetriaNotificationData.tracking.om_campagin — the SDK type literally spells the field om_campagin (in src/types.ts), but the docs at push-notifications/setup.md show the correct spelling om_campaign. The docs are misleading users: the field they'll actually receive in their tracking payload is the misspelled one. Best fix is in the SDK source on the next major.
  • isLoggingEnabled(enabled: boolean) is a setter despite the getter-style name — used correctly in troubleshooting.md, but the API surface is unclear. Worth renaming in the SDK (e.g. setLoggingEnabled) on the next major.
  • Deprecated methods (onMessageReceived, onDeepLinkInteracted, onNotificationInteracted, setBackgroundMessageHandler) — already correctly handled in the docs: every mention is either inside a "Deprecated as of …" admonition or recommends the replacement API. No action needed.
  • Firebase modular API vs namespaced API — the Expo and Bare React Native push-setup tabs use different RNFirebase API styles (getToken(messagingInstance) vs messaging().getToken()). Both work; reflects the modular API recommended for newer RNFirebase versions vs the legacy style. Worth aligning to modular in both tabs eventually, but not a defect.
