iOS Docs — Phase 2 Fixes for Review

12 fixes applied to documentation/docs-ios/, each cross-referenced against the live SDK source at ometria.ios_sdk @ master.

The new Docusaurus iOS docs were ported verbatim from the legacy README_ios.md, then reviewed for defects. Twelve issues were found and fixed; each item below shows the change, the file, the reason, and the SDK source line confirming it. Build verified clean (pnpm build, zero broken-link warnings).

Group 1 — Swift code that wouldn't compile

1NSE override: wrong method name and missing ()

File: docs-ios/push-notifications/notification-service-extension.md
-override func initializeOmetria -> Ometria? { return Ometria.initializeForExtension(appGroupIdentifier: "YOUR_App_GROUP_IDENTIFIER") }
+override func instantiateOmetria() -> Ometria? { return Ometria.initializeForExtension(appGroupIdentifier: "YOUR_APP_GROUP_IDENTIFIER") }

Why: Swift requires () on every function declaration, and the SDK's actual hook is instantiateOmetria() — not initializeOmetria as the README had it. Two bugs in one line. Also normalised the inconsistent App/APP casing in the placeholder string.

SDK source: OmetriaNotificationServiceExtension.swift declares open func instantiateOmetria() -> Ometria? as the override point.

2Bare return in a Bool-returning function

File: docs-ios/installation.md § 2
- return }
+ return true }

Why: application(_:didFinishLaunchingWithOptions:) returns Bool; a bare return won't compile.

3continue:restorationHandler: body never returned

File: docs-ios/deep-linking.md § "Process universal links inside the app"
- if let url = userActivity.webpageURL { Ometria.sharedInstance().processUniversalLink(url) { (url, error) in // ... } } }
+ if let url = userActivity.webpageURL { Ometria.sharedInstance().processUniversalLink(url) { (url, error) in // ... } return true } return false }

Why: Function signature returns Bool. The processUniversalLink callback is asynchronous, so the outer function returns true synchronously after kicking off the async call (and false if there's no webpageURL).

Group 2 — Documentation/data inconsistencies

File: docs-ios/events/basket-events.md § OmetriaBasket → Properties
Before * `currency`: (String, required) - … * `price`: (float, required) - A float value representing the pricing. * `items`: (Array[OmetriaBasketItem]) - … * `link`: (String) - … "Forgot to check out? Here's your basket to continue: ".
After * `id`: (String, optional) - A unique identifier for this basket. * `currency`: (String, required) - … * `totalPrice`: (Float, required) - A float value representing the pricing. * `items`: (Array[OmetriaBasketItem]) - … * `link`: (String, optional) - … "Forgot to check out? Why: The example code one paragraph above the table uses OmetriaBasket(id:, totalPrice:, currency:, items:, link:). The table now matches the example. Also restored the missing <link> placeholder in the example sentence (MDX was eating it as a JSX tag) using HTML entities.

SDK source: OmetriaBasket.swift init is (id: String? = nil, totalPrice: Float, currency: String, items: [OmetriaBasketItem] = [], link: String? = nil) — every type and optionality matches the corrected table.

Why: The example code uses OmetriaBasketItem(productId:, variantId:, sku:, quantity:, price:), but variantId was missing from the table. Inserted between productId and sku to match the example's parameter order.

6Ometria.initialize in "Disabling Swizzling" now shows the full signature

File: docs-ios/installation.md § 3
-Ometria.initialize(apiToken: "YOUR_API_TOKEN_HERE", enableSwizzling: false)
+Ometria.initialize(apiToken: "YOUR_API_TOKEN_HERE", enableSwizzling: false, appGroupIdentifier: "YOUR_APP_GROUP_IDENTIFIER")

Why: § 2 always passes appGroupIdentifier (which is needed because the App Group is created during NSE setup). The Swizzling example previously dropped that parameter, leaving readers unsure whether they had to pick one or the other. The revised call combines both flags in declared order.

SDK source: single overload initialize(apiToken: String, enableSwizzling: Bool = true, appGroupIdentifier: String? = nil) -> Ometria. Both flags are present together with defaults; Swift requires named arguments in declared order, hence enableSwizzling precedes appGroupIdentifier in the call.

Group 3 — Misleading or outdated content

7Option 1 reframed: it's a simpler way to write an NSE, not a way to skip one

File: docs-ios/push-notifications/setup.md § "Handling Push Notifications" → Option 1
Before Ometria provides a method that allows you to handle notifications directly in your app without creating a separate extension. This approach is simpler and works for most apps that want full push notification functionality. * … * No separate target or extension is needed * Ideal for apps that want to keep the setup simple while still supporting rich notifications
After Ometria provides a `handleNotification` method that wraps all the SDK's notification-handling logic into a single call. You still need to create a Notification Service Extension and configure the App Group (see [Notification Service Extension](./notification-service-extension.md) for the prerequisites) — this method just lets you replace the body of your `NotificationService.didReceive(_:withContentHandler:)` with a one-liner that delegates to Ometria. * … * You don't have to write the NSE logic yourself — just call this method from inside your `NotificationService` subclass * Ideal for apps that want to keep the setup simple while still supporting rich notifications

Why: The signature (request: UNNotificationRequest, contentHandler: @escaping (UNNotificationContent) -> Void) is the exact shape of UNNotificationServiceExtension.didReceive(_:withContentHandler:) — i.e. it must be called from inside an NSE. Option 1 is a thin wrapper, not a way to avoid the NSE entirely. Also, § 2's init takes appGroupIdentifier, which only makes sense if an NSE + App Group exist.

8AASA filename: apple_app_site_association → apple-app-site-association

File: docs-ios/deep-linking.md § "Create an apple-app-site-association file"
-Save it and name it "apple_app_site_association" (notice that no extension has been used…)
+Save it and name it "apple-app-site-association" (notice that no extension has been used…)

Why: Apple requires the filename apple-app-site-association (hyphens, no extension). With underscores the OS will not pick it up. The section heading already used the correct spelling — only the in-paragraph instruction was wrong.

9userNotificationCenter(_:didReceive:withCompletionHandler:) now calls its handler

File: docs-ios/installation.md § 3 "Disabling Swizzling"
-func userNotificationCenter(_ center: …, withCompletionHandler completionHandler: @escaping () -> Void) { Ometria.sharedInstance().handleNotificationResponse(response) }
+func userNotificationCenter(_ center: …, withCompletionHandler completionHandler: @escaping () -> Void) { Ometria.sharedInstance().handleNotificationResponse(response) completionHandler() }

Why: Apple's docs say not calling the completion handler can cause the app to be terminated. The neighbouring willPresent example already calls its handler.

10Removed deprecated pod setup step

File: docs-ios/installation.md § 1
-2. Run `pod setup` to create a local CocoaPods spec mirror.

Why: pod setup was deprecated in CocoaPods 1.8 (2019); the master spec repo is now set up automatically on first pod install. Remaining steps were renumbered.

11intro.md event-tracking bullet rephrased

File: docs-ios/intro.md
-1. Tracking customer behaviour through events - handled by Ometria. 2. Sending and displaying push notifications - **requires the app developers**.
+1. **Tracking customer behaviour** through events - a subset of events is automatically handled by the Ometria SDK, but you have to customize it to your needs. 2. **Sending and displaying push notifications** - requires the app developers.

Why: The original bullet implied event tracking was zero-effort. The Events page makes clear that most events are manually tracked. New wording matches the React Native intro.
